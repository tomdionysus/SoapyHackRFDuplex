# Compatibility

What has been run against the pair, on the target (Raspberry Pi 5,
Debian trixie, SoapySDR 0.8.1, libhackrf 2024.02.1, both boards on
firmware 2026.01.3, `clkout=rx`), with the module from the build tree
(`SOAPY_SDR_PLUGIN_PATH`). Each row says what was checked; a quirk is
named where there is one.

| Application | Version | Checked | Result |
|---|---|---|---|
| `SoapySDRUtil --find` | 0.8.1 | discovery, without opening a board | Two devices, one per ordering of the boards: device 0 with the lower serial receiving (the default), device 1 the other way round. Either set of arguments opens that pair. With SoapyHackRF (0.3.4) installed too, each board is also listed once under `driver=hackrf`; every run below after GNU Radio's install was made with both modules present. |
| `SoapySDRUtil --probe` | 0.8.1 | identification, settings, sensors, ranges per channel | Everything listed as designed (COMPLETED.md, item 5): one RX and one TX channel, full duplex, four formats, CS8 native, the `buffers` stream argument, clock and time sources, `ref_locked` and `time_locked`, `lo_locked` per channel. It reports "Timestamps: NO" because no origin holds until both streams run. |
| `SoapySDRUtil --rate` | 0.8.1 | receive and transmit (zeros) separately, 8 and 16 Msps, 12 s each | 7.99 and 15.99 Msps received, no overflow; transmit 8.2 and 16.2 Msps written (the ring filling first), no underflow. |
| SoapySDR Python bindings | 0.8.1, numpy 2.2.4 | `tools/timed_loopback.py`: a timed burst 5.5 transfers after a receive timestamp, 30 bursts at each of 2, 8 and 16 Msps, TX gain 0 | Every burst written was on time to the sample (+0, 30 of 30 at 2 and 8 Msps, 29 of 29 at 16 Msps). At 16 Msps one burst was lost to a receive gap when the Python reader fell behind once; a reader in Python must drain reads from samples already queued before taking the time from one, as the script does. |
| GNU Radio, Soapy source and sink | 3.10.12 | `tools/gnuradio_duplex.py`: one top block with a Soapy sink sending a tone and a Soapy source receiving it, 2 Msps 10 s, 8 and 16 Msps 60 s each, TX gain 0 | Works. GNU Radio makes the source and the sink each with its own `Device::make`, and SoapySDR hands both the one pair. The tone arrived where it was sent at every rate, the strongest signal away from the centre. At 16 Msps GNU Radio reports one overflow at start-up, every run, and none after: it activates the receive stream and then the transmit stream, the second activation sends the calibration burst (about 0.25 s), and nothing reads the receive stream meanwhile, which overflows the default ring of 15 transfers (123 ms at 16 Msps). The stream argument `buffers=40` held it (2 runs of 2 clean). |
| SoapyRemote | 0.5.2 | the pair served by `SoapySDRServer` on the target, its client in another process there | In progress. Discovery and `--probe` through the server list and describe the pair as locally. A duplex flowgraph through it delivered the tone at 2 Msps, but with dozens of write timeouts and overflows a run, with the host's socket buffers at 4 MiB (SoapyRemote asks for 42 MiB); one receive-only run ended in a stream error. Not yet concluded. |
| `hackrfduplex-ft8` (examples/ft8, an FT8 decoder through SoapySDR) | this repository | receive only on UTC slots at 144.174 MHz; `--loopback`, a timed FT8 frame each slot decoded back, at 868.3 MHz, TX gain 0 | Receive only ran clean, three whole slots, nothing to hear in the shielded box. The loopback decoded the frame in 3 slots of 3 at +17 to +18 dB SNR, on frequency and at 0.0 s time offset ([docs/examples.md](examples.md)). |
| A packaged receive-only application | | | Not yet run: none is installed on the target. |
