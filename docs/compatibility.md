# Compatibility

What has been run against the pair, on the target (Raspberry Pi 5,
Debian trixie, SoapySDR 0.8.1, libhackrf 2024.02.1, both boards on
firmware 2026.01.3, `clkout=rx`), with the module from the build tree
(`SOAPY_SDR_PLUGIN_PATH`). Each row says what was checked; a quirk is
named where there is one.

| Application | Version | Checked | Result |
|---|---|---|---|
| `SoapySDRUtil --find` | 0.8.1 | discovery, without opening a board | Two devices, one per ordering of the boards: device 0 with the lower serial receiving (the default), device 1 the other way round. Either set of arguments opens that pair. With SoapyHackRF (0.3.4) installed too, each board is also listed once under `driver=hackrf`; every run below after GNU Radio's install was made with both modules present. |
| `SoapySDRUtil --probe` | 0.8.1 | identification, settings, sensors, ranges per channel | Everything listed as designed (COMPLETED.md, item 5): one RX and one TX channel, full duplex, four formats, CS8 native, the `buffers` stream argument, clock and time sources, `ref_locked` and `time_locked`, `lo_locked` per channel. It reports "Timestamps: NO" because no origin holds until both streams run. |
| `SoapySDRUtil --rate` | 0.8.1 | receive and transmit (zeros) separately, 8 and 16 Msps, 12 s each | 7.99 and 15.99 Msps received, no overflow; transmit 8.2 and 16.2 Msps written (the ring filling first), no underflow. |
| SoapySDR Python bindings | 0.8.1, numpy 2.2.4 | `tools/timed_loopback.py`: a timed burst 5.5 transfers after a receive timestamp, 30 bursts at each of 2, 8 and 16 Msps, TX gain 0 | Every burst written was found, none refused, none lost (2026-11-12). At 2 and 8 Msps every one at +0. At 16 Msps 16 at +0 and 14 one sample early: the script finds the burst with its own correlator, while the module's calibration uses the module's finder, and when the delay between the boards falls near half a sample in a start the two round it opposite ways (as at 15.36 Msps, docs/design.md); the burst lands within half a sample of the time asked. A reader in Python must take the time from a read it waited for, not one that drains a backlog, as the script does. Quirk of the bindings, not the module: `SoapySDR.Device(dict(...))` finds no device for any driver (the stock `hackrf` alike); pass an argument string or a `SoapySDR.SoapySDRKwargs`. |
| GNU Radio, Soapy source and sink | 3.10.12 | `tools/gnuradio_duplex.py`: one top block with a Soapy sink sending a tone and a Soapy source receiving it, 2 Msps 10 s, 8 Msps 60 s, 16 Msps 60 s twice and 30 s once, TX gain 0, default stream arguments | Works. GNU Radio makes the source and the sink each with its own `Device::make`, and SoapySDR hands both the one pair. The tone arrived where it was sent at every rate, 33 to 34 dB above the median bin, with no overflow. It activates the receive stream and then the transmit stream, whose activation sends the calibration burst (about 0.25 s) while no block reads: the old fixed ring of 15 transfers (123 ms at 16 Msps) overflowed there every run, and needed `buffers=40`; the receive ring now holds 1.5 s at the rate, and no stream argument is needed. |
| SoapyRemote | 0.5.2 | the pair served by `SoapySDRServer` (from the build tree, on 127.0.0.1:55140) to clients in other processes on the target, the host's socket buffers left at their 208 KiB limit: a Python receiver 10 s at 2 and 8 Msps over UDP and TCP; `SoapySDRUtil --rate` each way at 2 and 8 Msps; the GNU Radio duplex flowgraph at 2 Msps, 20 s | Works. Received 99.3 to 99.8% of the rate with no overflow, timeout or error over either protocol; `--rate` 1.99 and 7.98 Msps received, 2.2 and 8.2 Msps transmitted (the ring filling first); the flowgraph's tone where it was sent. SoapyRemote's server reads a stream from `setupStream` on and passes its client every answer but a timeout, so the module's reads on a stream not yet started now time out as other drivers' do (before, 30 to 52 errors a run, and `--rate` quit at the first); its own keys (`remote`, `remote:mtu`, `remote:prot`, ...) pass without a warning. Over UDP, SoapyRemote marks a few transmit packets lost (`S`) against the 208 KiB socket buffers, against the 42 MiB it asks for; `remote:prot=tcp` as a device argument has none. |
| `hackrfduplex-ft8` (examples/ft8, an FT8 decoder through SoapySDR) | this repository | receive only on UTC slots at 144.174 MHz; `--loopback`, a timed FT8 frame each slot decoded back, at 868.3 MHz, TX gain 0 | Receive only ran clean, three whole slots, nothing to hear in the shielded box. The loopback decoded the frame in 3 slots of 3 at +17 to +18 dB SNR, on frequency and at 0.0 s time offset ([docs/examples.md](examples.md)). |
| rtl_433, a receive-only decoder for ISM-band sensors | 25.02 (Debian 25.02-1+deb13u1) | `-d driver=hackrfduplex,clkout=rx -f 868.3M -s 1024k -g LNA=16,VGA=20`, 60 s and 20 s | Works: it opens the pair through SoapySDR, lists its gains, rates, filters and formats, tunes, sets the gains, streams CS8 and exits cleanly. Nothing decoded, as nothing transmits in the shielded box. It reads the filter before setting one, which the device now answers with 7 MHz, the start-up rate's (it read 0 before the device opened at 10 Msps). Its listing shows every gain element as 0 to 116 dB: rtl_433 asks for the overall range once per element name (`sdr.c` line 807); the module's per-element ranges are LNA 0 to 40, VGA 0 to 62, AMP 0 to 14. |
